# Тестовое задание: Асинхронный сервис процессинга платежей

Сервис принимает платeж, сразу отвечает `202 Accepted`, обрабатывает его в фоне через эмулятор платeжного шлюза и сообщает результат клиенту вебхуком.

---

## Быстрый старт

Docker и `make`.

```bash
cp .env.example .env
make run
```

Через 30–40 секунд все сервисы будут `healthy`:

```bash
docker compose ps
```

Проверить, что API отвечает:

```bash
curl -s localhost:8080/health/ready
```

Ожидаемый ответ: `{"status":"ok", ...}`.

Документация API (Swagger): <http://localhost:8080/docs>

---

## Как  работает

```
Клиент --> POST --> API --> одна транзакция --> PostgreSQL (payments + outbox)
                                                │
                                   outbox-relay │ забирает события
                                                V
                               RabbitMQ: очередь payments.new
                                                │
                                       consumer │ обрабатывает
                                                V
                          шлюз заглушка (2–5 с, 90% успех) --> статус в БД -> вебхук клиенту
```

1. API сохраняет платeж и событие `payment.created` в таблицу `outbox` в одной транзакции. Событие не теряется, если RabbitMQ в этот момент недоступен.
2. outbox-relay раз в 0,5с забирает неотправленные события и публикует их в RabbitMQ с подтверждением доставки.
3. consumer берeт сообщение, вызывает эмулятор шлюза (для реализации задержки/90% успешных отправлений), сохраняет статус (`succeeded` или `failed`) и отправляет вебхук.
4. Если вебхук не дошeл, сообщение повторяется ещe 2 раза с паузой. После 3-й неудачи оно уходит в DLQ.

## API

Все запросы к `/api/v1/*` требуют заголовок `X-API-Key`. 
Значение берeтся из `.env` (по умолчанию `dev-api-key`).
Чтобы не вставлять ключ руками:

```bash
export API_KEY=$(grep '^API_KEY=' .env | cut -d= -f2-)
```

### Создать платeж

```bash
curl -s -X POST localhost:8080/api/v1/payments \
  -H "X-API-Key: $API_KEY" \
  -H "Idempotency-Key: order-42" \
  -H "Content-Type: application/json" \
  -d '{
        "amount": "1500.00",
        "currency": "RUB",
        "description": "Заказ №42",
        "metadata": {"order_id": 42},
        "webhook_url": "http://webhook-sink:9000/hook"
      }'
```

Ответ `202 Accepted`:

```json
{"payment_id": "8b0c…", "status": "pending", "created_at": "2026-11-10T12:00:00.123456Z"}
```

| Поле          | Правила                                                                                                    |
|---------------|------------------------------------------------------------------------------------------------------------|
| `amount`      | больше 0, не больше 2 знаков после запятой                                                                 |
| `currency`    | `RUB`, `USD` или `EUR`                                                                                     |
| `description` | 1–1000 символов                                                                                            |
| `metadata`    | JSON (необязательное поле)                                                                                 |
| `webhook_url` | `http` или `https`,(`localhost`, `10.x`, `169.254.x`) запрещены, кроме случая `WEBHOOK_ALLOW_PRIVATE=true` |

### Получить платeж

```bash
curl -s localhost:8080/api/v1/payments/<payment_id> -H "X-API-Key: $API_KEY"
```

Ответ `200 OK`:

```json
{
  "payment_id": "8b0c…",
  "amount": "1500.00",
  "currency": "RUB",
  "description": "Заказ №42",
  "metadata": {"order_id": 42},
  "status": "succeeded",
  "idempotency_key": "order-42",
  "webhook_url": "http://webhook-sink:9000/hook",
  "webhook_status": "delivered",
  "webhook_attempts": 1,
  "created_at": "…",
  "updated_at": "…",
  "processed_at": "…"
}
```

- `status`: `pending` -> `succeeded` или `failed`.
- `webhook_status`: `pending` -> `delivered` или `failed`. 
- Если вебхук не дошeл, статус самого платежа от этого не меняется.

### Коды ответов

| Код   | Событие                                                            |
|-------|--------------------------------------------------------------------|
| `202` | платeж принят (или повтор с тем же ключом)                         |
| `200` | данные платежа                                                     |
| `401` | нет `X-API-Key` или ключ неверный                                  |
| `404` | платeж не найден                                                   |
| `409` | `Idempotency-Key` уже использован с другим телом запроса           |
| `422` | ошибка валидации (тело, заголовок `Idempotency-Key`, `payment_id`) |
| `503` | бд недоступна                                                      |

## Идемпотентность

| Повтор запроса           | Результат                                                                                    |
|--------------------------|----------------------------------------------------------------------------------------------|
| тот же ключ, то же body  | `202`, тот же `payment_id`, заголовок `Idempotent-Replayed: true`. Новый платeж не создаeтся |
| тот же ключ, другое body | `409 Conflict`                                                                               |

Проверить можно, отправив запрос из примера выше дважды: `payment_id` будет одинаковым.
Body `{"amount": 100}` и `{"amount": "100.00"}` считаются одинаковыми, как и тела с другим порядком ключей.
Канкарент запросы с одним ключом создают ровно один платeж (в бд unique constraint).

## Вебхуки

Когда платeж обработан, consumer отправляет `POST` на `webhook_url`:

```json
{
  "event_id": "5111dc2b-…",
  "payment_id": "121dcacc-…",
  "status": "succeeded",
  "amount": "1500.00",
  "currency": "RUB",
  "processed_at": "2026-11-10T16:11:51.123Z"
}
```

Заголовки:
- `X-Event-Id` — уникальный id. Вебхук может прийти дважды (at least once), поэтому дубликаты стоит отбрасывать по id.
- `X-Webhook-Signature: sha256=<hex>` — sha body запроса с ключом `WEBHOOK_SECRET`.


Как consumer реагирует на ответ получателя:

| Ответ получателя                          | Стутас/Действие                              |
|-------------------------------------------|----------------------------------------------|
| `2xx`                                     | доставлено                                   |
| `408`, `429`, `5xx`, таймаут, ошибка сети | повторяем                                    |
| остальные `4xx`, редиректы `3xx`          | больше не пытаемся, `webhook_status=failed`  |

### Тестовый вебхук `webhook-sink`
Установлена переменная `"webhook_url": "http://webhook-sink:9000/hook"`, вебхуки приходят в `webhook-sink`.
Посмотреть, что пришло:
```bash
curl -s "localhost:9000/calls?payment_id=<payment_id>"
```

Для каждого вызова видно, валидность подписи (`signature_valid`) и дубликат ли.

Параметры вебхука тестовго:

|                                                                                                       | Параметр                                     |
|-------------------------------------------------------------------------------------------------------|----------------------------------------------|
| `curl -s -X POST localhost:9000/config -H "Content-Type: application/json" -d '{"fail_times": 1}'`    | первый вызов получит `503`, повтор пройдeт   |
| `curl -s -X POST localhost:9000/config -H "Content-Type: application/json" -d '{"status_code": 500}'` | все вызовы с ошибкой - после 3 попыток в DLQ |
| `curl -s -X POST localhost:9000/config -H "Content-Type: application/json" -d '{}'`                   | обычный режим                                |

> `POST /config` заменяет настройки целиком, а не дополняет их.

## Повторы и DLQ

Если вебхук не дошeл или упала обработка (например, недоступна БД), сообщение повторяется с экспоненциальной задержкой:

```
попытка 1 - ждeм 2с - попытка 2 -> ждeм 4с -> попытка 3 -> DLQ
```

Паузы реализованы очередями RabbitMQ с TTL (`payments.new.retry.2000ms`, `payments.new.retry.4000ms`), consumer не простаивает, пока ждeт.
Сломанные сообщения (невалидный JSON, несуществующий платeж) уходят в DLQ сразу, без повторов.
Отказ шлюза (10% от всех запросов) — это указано в ТЗ, платeж получает `status=failed`, клиент получает вебхук, повторов нет.

### Посмотреть DLQ

```bash
make dlq-list
```

Или в веб-интерфейсе RabbitMQ: <http://localhost:15672> -> Queues -> `payments.new.dlq`.

### Отправить сообщения из DLQ заново

Когда получатель вебхуков починился:

```bash
make dlq-replay
```
Команда переоткрывает вебхук платежа (`failed` -> `pending`) и возвращает сообщение в `payments.new` с обнулeнным счeтчиком попыток. 
Невалидные сообщения остаются в DLQ. Ограничить количество: `make dlq-replay limit=10`.

## Тесты

| Команда      | Что проверяет                                                                   | Где выполняется                                                                                      |
|--------------|---------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------|
| `make check` | линтер + все тесты (pytest)                                                     | локально. Тестам нужны запущенные `db` и `rabbitmq` из `make run`, без них часть тестов пропускается |
| `make e2e`   | сквозной сценарий на живом стеке (15 проверок)                                  | отдельный стек `basis-test`                                                                          |
| `make chaos` | сбои: падение RabbitMQ, relay, consumer, ошибки вебхука, доля успешных платежей | отдельный стек `basis-test`                                                                          |

**Тестовые данные работают с тестовой бд:**
- pytest использует отдельную базу `basis_test` и очищает еe после прогона;
- `make e2e` и `make chaos` поднимают отдельный стек `basis-test` (своя БД и RabbitMQ, порты 18080 и 19000) и удаляют его в конце.

При необходисостти:
- оставить тестовый стек после прогона для отладки: `KEEP_STACK=1 make e2e`;
- удалить его потом: `make test-stack-down`;
- запустить только часть сбоев: `make chaos scenarios="c1 c3"`.

| Сценарий   | Что происходит                            | Что должно получиться                                                   |
|------------|-------------------------------------------|-------------------------------------------------------------------------|
| C-1        | RabbitMQ остановлен, создаeм 5 платежей   | все `202`, события ждут в outbox, после запуска RabbitMQ все доставлены |
| C-2        | relay убит во время обработки 50 платежей | все доставлены, outbox пуст                                             |
| C-3        | consumer убит во время обработки          | после перезапуска всe обработано                                        |
| C-4        | получатель вебхуков всегда отвечает `500` | 3 попытки, затем DLQ                                                    |
| C-5        | 200 платежей                              | ~90% успешных                                                           |

## Настройки

Все настройки задаются через .env файл:

| Переменная                                | По умолчанию         | Назначение                                                        |
|-------------------------------------------|----------------------|-------------------------------------------------------------------|
| `API_KEY`                                 | `dev-api-key`        | ключ для `X-API-Key`. Без него API не запустится                  |
| `WEBHOOK_SECRET`                          | `dev-webhook-secret` | ключ подписи вебхуков. Без него consumer не запустится            |
| `WEBHOOK_ALLOW_PRIVATE`                   | `true` в Docker      | разрешить вебхуки на внутренние адреса (нужно для `webhook-sink`) |
| `GATEWAY_DELAY_MIN` / `GATEWAY_DELAY_MAX` | `2` / `5`            | задержка эмулятора шлюза, секунды                                 |
| `GATEWAY_SUCCESS_RATE`                    | `0.9`                | доля успешных платежей                                            |
| `RETRY_MAX_ATTEMPTS`                      | `3`                  | сколько всего попыток до DLQ                                      |
| `RETRY_BASE_DELAY_MS`                     | `2000`               | первая пауза между попытками, дальше удваивается                  |
| `CONSUMER_PREFETCH`                       | `10`                 | сколько платежей consumer обрабатывает одновременно               |
| `CONSUMER_GRACEFUL_TIMEOUT`               | `15`                 | сколько секунд consumer дожидается текущих платежей при остановке |
| `OUTBOX_POLL_INTERVAL`                    | `0.5`                | как часто relay проверяет outbox, секунды                         |
| `OUTBOX_RETENTION_DAYS`                   | `7`                  | через сколько дней удалять отправленные события из outbox         |

Полный список — в `src/core/config.py`.

## Docker Compose

Конфигурация разбита на три файла:

| Файл                      | Для чего                                                      |
|---------------------------|---------------------------------------------------------------|
| `docker-compose.yml`      | общая часть: сервисы, переменные, healthcheck                 |
| `docker-compose.dev.yml`  | разработка: порты на хосте, код монтируется из `./src`        |
| `docker-compose.test.yml` | изолированный стек `basis-test` для `make e2e` и `make chaos` |

`COMPOSE_FILE` в `.env` указывает на общий и dev-файл, поэтому обычные команды `docker compose …` работают с dev-стеком.

## Решения и ограничения

- Доставка at leastonce. Сообщение или вебхук может прийти повторно. Каждый шаг обработки идемпотентен: статус платежа меняется ровно один раз, нет повторного списывания.
- outbox-relay — отдельный сервис, в задании перечислены только `postgres`, `rabbitmq`, `api` и `consumer`. Но API не зависит от RabbitMQ, а relay можно перезапускать и масштабировать отдельно.
- Сервис базы данных называется `db` (контейнер `basis-db`).
- Защита от SSRF. Адрес вебхука проверяется и при создании платежа, и перед отправкой (после DNS-резолва). Остаeтся узкое окно, если DNS-запись подменят между проверкой и подключением.
- webhook-sink — только для разработки и тестов, в продакшене он не нужен.
